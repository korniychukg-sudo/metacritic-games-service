# Metacritic Games Digest

Сервис раз в час заходит на Metacritic в раздел Games, берёт 20 новых игр, которые сегодня ещё не обрабатывал,
и сохраняет их в свою базу. Если игра уже есть в базе, сервис её обновляет. Для каждой игры он делает
отдельные резюме отзывов критиков и отзывов игроков: что нравится и что нет. Ещё он находит самый популярный
летсплей на YouTube, переводит речь блогера в текст и пишет по этому тексту заключение. Всё это видно
в веб-интерфейсе, там же есть мониторинг работы сервиса в реальном времени и кнопка принудительного запуска.

Тестовое задание на позицию AI Automation Engineer. Сервис работает без единого секрета: LLM по умолчанию
вызывается через бесплатный анонимный эндпоинт, Metacritic и YouTube читаются без ключей.

## Возможности

| Требование задания | Как сделано |
|---|---|
| Раз в час 20 новых игр | Фоновый планировщик (`app/scheduler.py`) запускает обработку каждые `RUN_INTERVAL_MINUTES` (60) минут. Интервал отсчитывается от старта последнего запуска любого типа и хранится в БД, поэтому переживает перезапуск. Ручной запуск считается слотом: следующий плановый будет через час после него. Если слот наступил, а обработка ещё идёт, планировщик не теряет слот, а ждёт её окончания. |
| Первый проход дня: New Releases | Первые 20 игр берутся из блока New Releases на `/game/`. Источник: тот же JSON, из которого Metacritic рендерит этот блок (`finder ... new-releases-carousel`, порядок совпадает 1:1). |
| Следующие проходы: SEE ALL, сортировка «новые» | Страницы `/browse/game/all/all/all-time/new/` (JSON `finder ... sortBy=-releaseDate`, 24 игры на страницу). Курсор страницы хранится по дням (`day_state`). Страница считается пройденной, только когда обработаны все игры на ней. Если страница не поместилась в пачку или запуск остановился раньше, следующий запуск продолжит с неё же. |
| Сегодня не обрабатывал / новый день заново | Таблица `processed(day, game_id)` хранит, что обработано за день. Новый день начинается с New Releases, курсор стоит в начале. Границы дня считаются по `DAY_TZ` (по умолчанию Москва); запуск, перешедший через полночь, засчитывается дню своего старта. Игра, на которой запуск упал (например, 5xx от Metacritic), повторяется в тот же день, но не больше `FAILED_GAME_MAX_ATTEMPTS` (2) раз. |
| Добавить или обновить | Upsert по id тайтла Metacritic. У игры растёт счётчик `times_processed`. Если Metacritic вернул неполные данные (нет платформ или блока отзывов), сохранённые платформы, отзывы и резюме не затираются, а в мониторинге появляется ошибка с пометкой `schema`. |
| Название, обложка, разработчик, описание, видео | Всё берётся из одного запроса composer: `product` (обложка `cardImage`, разработчики из `production.companies`, видео JW Player `embedUrl` и HLS `manifestUrl`). Если у игры на Metacritic видео нет, сервис находит официальный трейлер на YouTube и показывает его с пометкой об источнике, так что ссылка на видео есть почти у каждой игры. |
| Платформы + Metascore + Userscore | Metascore по каждой платформе берётся из `product.platforms[]`. Userscore ведущей платформы приходит в composer, по остальным платформам сервис делает отдельный запрос. Ноль без оценок хранится как «нет оценки». |
| Резюме отзывов отдельно для критиков и игроков | Выборка 7/7/7 (positive / mixed / negative) из composer. Если негативных отзывов в выборке мало, сервис догружает негативные. Дальше LLM, ответ строго в JSON `likes/dislikes/verdict` на русском. При повторных обходах резюме пересчитывается, только если изменился набор отзывов (хэш). |
| Веб: список, карточка, фильтр по платформам, поиск, сортировка по рейтингу | Серверный рендеринг на Jinja2. Фильтр по платформе меняет и сами оценки: показываются и сортируются оценки выбранной платформы. Сортировка по Metascore и Userscore в обе стороны, а также по дате и названию. Поиск по подстроке названия без учёта регистра (символы `%` и `_` ищутся буквально). |
| Похожие игры | Считаются по уже загруженным играм: TF-IDF по описанию с косинусной близостью, плюс совпадения франшизы, разработчика, жанров и платформ (взвешенная сумма). Совпадения одних только платформ недостаточно, нужен содержательный сигнал. Пересчитываются после каждого запуска. В карточке до 5 похожих игр с причинами, по клику открывается их карточка. |
| Доп. 1: летсплей | YouTube-поиск без API-ключа: сортировка Popularity, ролики длиннее 20 минут, два запроса (`let's play` и `прохождение`). Сервис отсекает трейлеры и обзоры, проверяет, что название игры есть в названии ролика, предпочитает let's play / walkthrough / прохождение и из оставшихся берёт ролик с максимумом просмотров. Речь блогера переводится в текст через субтитры YouTube (ручные или автоматические, ASR), библиотека `youtube-transcript-api`. По расшифровке LLM пишет заключение: summary, плюсы, минусы, вердикт. Ссылка на ролик и фрагменты расшифровки сохраняются в карточке. |
| Доп. 2: мониторинг и кнопка | Страница `/monitor` получает обновления по Server-Sent Events (`/api/events`). На ней видны статусы воркеров (планировщик, обработчик, Metacritic, YouTube, LLM), прогресс текущего запуска (игра и шаг), счётчики за день и всего, ошибки, история запусков и живой журнал. Кнопка «Запустить обработку сейчас» доступна всем, но защищена от злоупотреблений (см. ниже). |

## Архитектура

```
             ┌────────────── FastAPI (app/main.py) ───────────────┐
 браузер ──▶ │  /  /game/{slug}  /monitor   Jinja2 + app.js        │
             │  /api/games  /api/status  /api/events (SSE)        │
             │  POST /run · POST /api/run · /healthz              │
             └──────┬──────────────────────────────┬──────────────┘
                    │ читает                       │ RunGuard → start_background()
              ┌─────▼─────┐   пишет   ┌────────────▼─────────────┐  каждый час
              │  SQLite   │◀──────────│ Pipeline (app/pipeline)  │◀─ Scheduler
              │ миграции, │  lease    │  select_batch → игра →   │
              │ lease     │           │  резюме → трейлер →      │──▶ Monitor
              └───────────┘           │  летсплей → похожие      │   (статусы, лог)
                                      └──┬─────────┬─────────┬───┘
                     PoliteClient ≤1 rps │         │         │ последовательно, пауза
                       ┌─────────────────▼┐ ┌──────▼──────┐ ┌▼──────────────────┐
                       │ backend.metacritic│ │  YouTube    │ │ OpenAI-совместимый│
                       │ finder / composer │ │ search/watch│ │ chat API (LLM)    │
                       │ reviews stats     │ │ + субтитры  │ │ + запасной режим  │
                       └───────────────────┘ └─────────────┘ └───────────────────┘
```

Модули:

- `app/metacritic.py`: клиент и парсеры JSON-бэкенда Metacritic (finder, composer, reviews, stats). Если
  формат ответа изменился, парсер бросает `SchemaError`, а не возвращает пустой список. Ссылки из ответов
  проходят белый список схем и хостов (видео только `https://cdn.jwplayer.com`).
- `app/selection.py`: чистая логика выбора пачки (повторы упавших игр, New Releases, затем SEE ALL).
- `app/youtube.py`: разбор выдачи (`ytInitialData`), выбор летсплея и трейлера, страница ролика,
  расшифровка. Страница согласия, капча или страница без `ytInitialData` распознаются как ошибка.
- `app/llm.py`: клиент OpenAI-совместимого API: очередь с паузой между вызовами, ретраи с backoff
  и `Retry-After`, извлечение JSON из ответа, предохранитель (см. «Запасные режимы»).
- `app/summarize.py`: промпты, валидация ответов (только русский язык), экстрактивные резюме.
- `app/similarity.py`: похожие игры (TF-IDF + метаданные) без внешних библиотек.
- `app/pipeline.py`: один запуск. Ошибка в одной игре не останавливает запуск, учёт запуска в `finally`.
- `app/scheduler.py`: фоновый поток, `tick()` без собственных часов, поэтому покрыт тестами.
- `app/monitor.py`: состояние воркеров, счётчики, кольцевой буфер логов для SSE.
- `app/db.py`: схема SQLite (WAL), миграции через `PRAGMA user_version`, пул соединений, lease запуска.
- `app/serve.py`: точка входа контейнера (порт из `PORT`, доверие прокси, понижение прав).

Как сервис обращается с внешними сервисами:

- Браузерный User-Agent.
- Не больше одного запроса в 1,1 с на каждый хост. Через этот же лимитер идут и запросы библиотеки
  субтитров.
- Таймауты 30 с.
- 3 ретрая с экспоненциальной паузой на 429/5xx и сетевые ошибки, `Retry-After` учитывается (до 60 с).
  404 и 403 не ретраятся.
- Летсплей перепроверяется раз в `LETSPLAY_REFRESH_DAYS` (7) дней, если заключение построено по
  расшифровке, и раз в `LETSPLAY_RETRY_HOURS` (24) часа, если результат неполный (нет расшифровки, нет
  ролика, ошибка). Трейлер с YouTube ищется раз в `TRAILER_REFRESH_DAYS` (7) дней и только для игр
  без видео на Metacritic.

На одну игру обычно уходит 2–5 запросов к Metacritic и 3–6 к YouTube (при повторных обходах в тот же
день к YouTube запросов нет).

### Запасные режимы (карточка никогда не пустая)

- **LLM не ответила.** Вместо её резюме строится экстрактивное: ключевые фразы из положительных
  и отрицательных отзывов. В карточке оно помечено как «цитаты без LLM». В конце каждого запуска сервис
  пробует пересчитать через LLM до `LLM_BACKFILL_LIMIT` таких резюме и заключений по летсплеям. Очередь
  досчёта идёт по давности последней попытки, поэтому одна «трудная» игра не блокирует остальные.
- **LLM лежит.** После `LLM_MAX_CONSECUTIVE_FAILURES` (3) неудачных вызовов подряд LLM до конца запуска
  не вызывается: резюме строятся из цитат, а досчёт на следующих запусках их улучшит. Это ограничивает
  время запуска при недоступной LLM.
- **Запуск затянулся.** Через `RUN_MAX_MINUTES` (50) минут запуск перестаёт брать новые игры (статус
  «остановлен по времени»), оставшиеся достаются следующему запуску. Так запуски не наезжают друг на друга.
- **Нет расшифровки у самого популярного ролика.** Сервис берёт следующий кандидат, до 3 штук. Если
  расшифровки нет ни у одного, заключение строится по названию и описанию ролика
  (`llm-description` / `description`). Если нет и описания, сохраняется только ссылка с пометкой о причине.
- **Metacritic или YouTube сменили формат.** Пустой список при `totalResults > 0`, отсутствие `data.items`,
  `product`, `ytInitialData`, страница согласия или капча считаются ошибкой (`... :schema` в мониторинге),
  а не «нечего обрабатывать». Если недоступен New Releases, запуск идёт по SEE ALL, а блок New Releases
  остаётся открытым до следующего запуска. Сохранённые данные при этом не затираются.
- **Метод в данных.** В каждом резюме записано, каким способом оно получено: `method`
  (`llm`, `extractive`, `llm-transcript`, `extractive-transcript`, `llm-description`, `description`, `none`).
  В интерфейсе метод показан бейджем.

### Принудительный запуск и защита

Кнопка на `/monitor` работает без логина, чтобы проверяющий мог ей пользоваться, но:

- одновременно идёт только один запуск (lock в процессе + lease в БД), повторный запрос получает 409;
- после окончания любого запуска действует пауза `MANUAL_RUN_COOLDOWN_SECONDS` (300 с): ответ 429
  с заголовком `Retry-After`, на кнопке обратный отсчёт;
- не больше `MANUAL_RUNS_PER_DAY` (24) ручных запусков в сутки (плановые не считаются);
- `POST /run` и `POST /api/run` принимают только запросы с этого же сайта (`Sec-Fetch-Site`/`Origin`),
  кросс-доменный POST получает 403;
- если задан `RUN_TOKEN`, `POST /api/run` требует `Authorization: Bearer <RUN_TOKEN>`. Кнопка на странице
  ходит в `POST /run` и продолжает работать без токена.

Прочее: шаблоны с автоэкранированием, ссылки в шаблонах проходят фильтр схем (только http/https),
заголовки `Content-Security-Policy` (без inline-скриптов и inline-стилей), `X-Content-Type-Options`,
`X-Frame-Options`, `Referrer-Policy`; параметры `page` (1–10000) и `q` (до 200 символов) валидируются.

## Запуск локально

Нужен Python 3.11+.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m app.serve          # или: .venv/bin/uvicorn app.asgi:app --port 8000
```

Откройте http://127.0.0.1:8000. При пустой базе первая обработка стартует сама примерно через 15 секунд.
Её ход видно на http://127.0.0.1:8000/monitor. Для быстрой проверки можно уменьшить пачку:
`BATCH_SIZE=4 .venv/bin/python -m app.serve`. Также можно запустить обработку вручную:
`curl -X POST 'localhost:8000/api/run?limit=3'`.

Тесты (153 шт.) работают офлайн, на сохранённых ответах из `docs/samples/`, время в них подменяется,
поэтому часовой интервал, смена дня и лимиты проверяются без ожидания:

```bash
.venv/bin/python -m pytest
```

Docker:

```bash
docker build -t mc-digest .
docker run -p 8000:8000 -v mc-data:/data mc-digest
```

Контейнер стартует от root только для того, чтобы выдать права на `/data` (у примонтированного volume
владелец root), и сразу понижает права до пользователя `app` (uid 10001), под которым работает uvicorn.

### Деплой (Railway)

В репозитории есть `Dockerfile` и `railway.json`: сборка из Dockerfile, healthcheck `/healthz`, одна реплика.

1. Создайте сервис из репозитория, переменные окружения не обязательны.
2. Подключите Volume с mount path `/data`. `DB_PATH=/data/games.db` уже задан в Dockerfile, без volume база
   пропадёт при пересборке. (`VOLUME` в Dockerfile не используется: Railway такие образы не принимает.)
3. Сервис слушает порт из `PORT`, который выставляет Railway. Uvicorn запускается с `--proxy-headers
   --forwarded-allow-ips="*"`, чтобы схема и адрес клиента брались из заголовков прокси Railway.

Важно: только одна реплика и один процесс. Не используйте `--workers N`, `--reload` и `numReplicas > 1`:
планировщик живёт в веб-процессе, а SQLite на volume рассчитан на один инстанс. Lease в БД не даст двум
процессам запустить обработку одновременно и не позволит закрыть чужой живой запуск, но несколько
планировщиков всё равно будут лишней нагрузкой.

`Procfile` нужен только для PaaS без Docker и запускает тот же `python -m app.serve`.

## Переменные окружения

Все необязательны. Числовые значения ограничиваются разумными пределами (например, интервал не меньше
1 минуты), неизвестный часовой пояс заменяется на UTC с предупреждением в логе.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `8000` | порт HTTP |
| `DB_PATH` | `./data/games.db` (в Docker `/data/games.db`) | файл SQLite |
| `BATCH_SIZE` | `20` | игр за один запуск |
| `RUN_INTERVAL_MINUTES` | `60` | интервал планировщика (минимум 1) |
| `RUN_MAX_MINUTES` | `50` | после этого времени запуск не берёт новые игры |
| `SCHEDULER_ENABLED` | `1` | `0` выключает автозапуск, ручная кнопка при этом работает |
| `STARTUP_DELAY_SECONDS` | `15` | задержка первого запуска после старта, если пора запускаться |
| `DAY_TZ` | `Europe/Moscow` | часовой пояс, по которому считается «сегодня» |
| `FAILED_GAME_MAX_ATTEMPTS` | `2` | сколько раз за день пробовать игру, на которой запуск упал |
| `BROWSE_PAGE_SIZE` / `BROWSE_MAX_PAGES` | `24` / `4` | размер страницы SEE ALL и предел страниц за запуск |
| `MANUAL_RUN_COOLDOWN_SECONDS` | `300` | пауза после окончания запуска, прежде чем можно запустить вручную |
| `MANUAL_RUNS_PER_DAY` | `24` | лимит ручных запусков в сутки, `0` без лимита |
| `RUN_TOKEN` | пусто | если задан, `POST /api/run` требует `Authorization: Bearer <RUN_TOKEN>` |
| `LLM_BASE_URL` | `https://text.pollinations.ai/openai` | любой OpenAI-совместимый API (к адресу добавляется `/chat/completions`) |
| `LLM_API_KEY` | пусто | ключ. Без ключа заголовок `Authorization` не отправляется |
| `LLM_MODEL` | `openai` | модель |
| `LLM_TIMEOUT` | `60` | таймаут одного вызова LLM, с |
| `LLM_RETRIES` | `3` | попыток на один вызов |
| `LLM_MIN_GAP_SECONDS` | авто | минимальный интервал между началами вызовов LLM: 32 с для анонимного Pollinations, 3 с для остальных |
| `LLM_MAX_PROMPT_CHARS` | авто | бюджет промпта в символах: 6000 для анонимного Pollinations, 9000 для остальных. Уменьшается только для текущего вызова: при ответе 413 или пустом ответе |
| `LLM_MAX_CONSECUTIVE_FAILURES` | `3` | после стольких неудач подряд LLM пропускается до конца запуска |
| `LLM_REASONING_EFFORT` | авто | `reasoning_effort` в запросе: `low` для анонимного Pollinations, не отправляется для остальных; `none` отключает |
| `LLM_BACKFILL_LIMIT` | `4` | сколько резюме из запасного режима пересчитывать через LLM за запуск |
| `LLM_ENABLED` | `1` | `0` отключает LLM, остаются только экстрактивные резюме |
| `YOUTUBE_ENABLED` | `1` | летсплеи и трейлеры с YouTube |
| `YOUTUBE_TRAILER_FALLBACK` | `1` | искать трейлер на YouTube, если на Metacritic видео нет |
| `YOUTUBE_PROXY_URL` | пусто | HTTP(S)-прокси для расшифровок (нужен на облачных IP, см. ниже) |
| `LETSPLAY_REFRESH_DAYS` | `7` | как часто перепроверять летсплей с заключением по расшифровке |
| `LETSPLAY_RETRY_HOURS` | `24` | как часто перепроверять неполный результат (нет расшифровки, ролика, ошибка) |
| `TRAILER_REFRESH_DAYS` | `7` | как часто перепроверять трейлер с YouTube |
| `HTTP_MIN_INTERVAL` | `1.1` | минимальная пауза между запросами к одному хосту, с |
| `ERRORS_KEEP_DAYS` / `PROCESSED_KEEP_DAYS` | `14` / `30` | сколько дней хранить журнал ошибок и учёт обработанных игр |
| `FORWARDED_ALLOW_IPS` | `*` | каким прокси доверять заголовки `X-Forwarded-*` (`app.serve`) |

## API

- `GET /api/games?q=&platform=&sort=&page=`: список.
  `sort` ∈ `date_desc|date_asc|metascore_desc|metascore_asc|userscore_desc|userscore_asc|title|updated`.
- `GET /api/games/{slug}`: полная карточка, включая похожие игры и `video` (источник, ссылка, embed).
- `GET /api/platforms`: платформы с количеством игр.
- `GET /api/status`: состояние воркеров, счётчики, история запусков, ошибки, состояние кнопки запуска
  (`manual`) и планировщика (`scheduler`).
- `GET /api/events`: поток SSE (`event: status`, `event: log`).
- `POST /api/run[?limit=N]`: запустить обработку. 202 запущено, 409 уже идёт, 429 пауза или дневной лимит
  (с `Retry-After`), 403 кросс-доменный запрос, 401 нет `RUN_TOKEN` (если он задан).
- `POST /run`: то же для кнопки на странице (без токена). С `Accept: application/json` отвечает JSON,
  иначе редиректит на `/monitor`.
- `GET /healthz`: 200, если БД доступна и планировщик жив и не просрочил запуск; иначе 503 с деталями.
- `GET /docs`: Swagger UI.

## Хранение данных

SQLite в режиме WAL. Схема версионируется через `PRAGMA user_version`: при старте сервис применяет
недостающие миграции из `app/db.py` одной транзакцией, база старой версии обновляется на месте, база новее
кода не открывается. Соединения берутся из ограниченного пула (8). Журнал ошибок и учёт обработанных игр
чистятся от старых записей в начале каждого запуска.

## Известные ограничения

- **Бесплатная LLM.** Анонимный Pollinations (`model=openai`, на деле `gpt-oss-20b`) пропускает примерно один
  запрос в 30 секунд с одного IP. Если запросы идут чаще, он отвечает `402` с пустым телом (замерено 14.10.2026),
  поэтому для анонимного Pollinations `402` считается лимитом частоты: сервис ждёт и повторяет, промпт не
  урезает. Модель рассуждающая, и у анонимного тарифа ответ ограничен 1500 токенами: на длинной расшифровке
  без настройки она тратила их все на рассуждения и возвращала пустой `content` (`finish_reason=length`),
  причём одинаковый запрос Pollinations отдаёт из кэша, так что простой повтор не помогает. Поэтому сервис
  отправляет `reasoning_effort: low` (ответ за 5–8 с вместо 15–20), а на пустой ответ повторяет вызов
  с укороченным промптом. Вызовы идут строго по очереди, с интервалом 32 с между началами. На игру уходит до трёх вызовов:
  критики, игроки, летсплей. Резюме по отзывам игроков без отзывов не запрашивается. Полная пачка из 20 игр
  обрабатывается примерно за 30–40 минут и укладывается в часовой интервал, а лимит `RUN_MAX_MINUTES`
  страхует от наложения запусков. С собственным ключом любого OpenAI-совместимого провайдера (`LLM_BASE_URL`,
  `LLM_API_KEY`, `LLM_MODEL`) интервал 3 с и пачка проходит за несколько минут. Модель иногда отвечает
  по-английски на английские отзывы. Такой ответ отбрасывается валидатором и запрашивается повторно.
- **Расшифровки YouTube с облачных IP.** С облачных IP (Railway, AWS, GCP) YouTube обычно блокирует
  получение субтитров (`RequestBlocked`). Тогда сервис переходит к заключению по описанию ролика и
  перепроверяет летсплей не чаще раза в сутки. Чтобы получать полноценные расшифровки на хостинге, нужен
  `YOUTUBE_PROXY_URL` (резидентный прокси). Локально всё работает.
- **Расшифровка = субтитры YouTube.** «Перевод речи в текст» выполняет ASR самого YouTube. Скачивание
  аудио и Whisper (yt-dlp + модель) не включены, потому что это тяжело для бесплатного хостинга.
  В коде для них есть точка расширения (`YouTubeClient.transcript`).
- **Запросы субтитров.** Библиотека `youtube-transcript-api` делает несколько HTTP-запросов на один ролик.
  Каждый из них проходит через общий лимитер (не чаще раза в 1,1 с), но собственные ретраи сервиса на них
  не распространяются: ошибка означает «расшифровки нет», и сервис берёт следующий ролик.
- **Строгое сопоставление названий роликов.** Номер части и подзаголовок игры обязаны быть в названии
  ролика, иначе легко взять летсплей другой игры серии (Space Marine 2 вместо Boltgun 2). Обратная сторона:
  у переизданий с отдельным подзаголовком (Dragon's Dogma 2: Dark Arisen) летсплей может не найтись, пока
  не появятся ролики с полным названием. Такой результат перепроверяется раз в сутки.
- **Выборка отзывов.** Отзывы берутся из выборки Metacritic (до 7 на тональность, ведущая платформа)
  и при необходимости догружаются негативными. Это не весь корпус отзывов.
- **Userscore у свежих игр.** У игр, вышедших сегодня, Userscore часто ещё нет, и в интерфейсе стоит «—».
- **Стабильность порядка.** Порядок игр с одинаковой датой релиза в выдаче Metacritic нестабилен, а ответы
  кэшируются Cloudflare. Дедупликация идёт по id, поэтому повторов нет. Но если в течение дня в начало
  списка добавится много новых игр, страницы сдвинутся, и отдельные игры могут попасть в обработку
  только на следующий день.
- **Один процесс.** См. раздел про деплой: одна реплика, без `--workers`.
- **Сложность похожих игр.** Пересчёт идёт целиком, примерно O(n²) по играм с общими терминами. Для
  нескольких тысяч игр это секунды, для сотен тысяч понадобился бы ANN-индекс.
- **Неофициальный API.** У Metacritic нет публичного API. Используется тот же JSON-бэкенд, что и у их
  сайта, без ключа. Если он начнёт требовать `apiKey`, ключ можно брать из HTML `/game/` (описано
  в `docs/DATA_SOURCES.md`). Запасной вариант с разбором `__NUXT_DATA__` тоже описан там.
